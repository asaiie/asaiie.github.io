Making gVisor Filesystems Faster with EROFS

September 4, 2026

This summer at Modal, I worked on improving filesystem performance for workloads running inside gVisor. One of the largest improvements came from replacing ImageFS with EROFS as the default filesystem for container images.

The change made metadata-heavy operations as much as 12 times faster while preserving the performance of large reads.

Some context

At Modal, user code runs in sandboxed containers. Those containers use gVisor, an application kernel that sits between a program and the host Linux kernel. Instead of allowing every system call to reach the host directly, gVisor implements much of the Linux system interface in a userspace process called the sentry.

A container also needs a filesystem. Most of its files come from a read-only container image: the operating-system files, libraries, packages, and source code that were present when the image was built. Before this project, Modal exposed those files to gVisor using an internal system called ImageFS.

ImageFS presented the container image as a normal directory tree owned by the host. It worked, but it meant that gVisor had to ask the host for help each time an application looked up a path, inspected metadata, or read a directory. That overhead becomes significant in workloads that touch thousands of files.

The read path with ImageFS

When an application inside a sandbox opened a file, read a directory, or requested file metadata, the operation first trapped into the gVisor sentry.

The sentry then made a host system call, which traveled through the host VFS and a FUSE mount before reaching the ImageFS server. ImageFS resolved the requested path or metadata and retrieved data from Blobnet when necessary.

This meant that even simple operations such as stat and readdir crossed the sandbox boundary and entered the host kernel. A workload that examined thousands of files had to pay this cost thousands of times.

Moving metadata into the sandbox

EROFS, short for Enhanced Read-Only File System, takes a different approach. Instead of exposing an entire host-owned file tree, it packages the container image as a block-structured filesystem image.

The sparse EROFS image is memory-mapped into the sentry. gVisor's EROFS driver can then parse its superblock, inodes, and directory entries directly from memory. Operations such as directory traversal and metadata lookup no longer require host system calls.

File contents still travel through the host VFS and FUSE mount when they are not already in the page cache. The important difference is that the FUSE server now serves one image file rather than resolving every operation against a full file tree.

In short, metadata stays inside the sandbox; only reads need to cross into the host.

Results

This design has its largest effect on workloads that inspect or manipulate many files:

Benchmark ImageFS EROFS Speedup
agentic 168.98s 45.33s 3.7×
chown 15.72s 5.59s 2.8×
find-all 2.78s 0.23s 12.1×
ripgrep 9.48s 3.53s 2.7×
bun install 10.38s 4.14s 2.5×

Large sequential reads remained effectively unchanged. A cold parallel read moved from 0.61 seconds to 0.63 seconds, while a warm read remained at 0.05 seconds. These operations still reach the FUSE mount when they miss the page cache, so they primarily measure the two FUSE server implementations rather than the in-memory metadata path.

Writes also do not meaningfully exercise either filesystem. gVisor sends them to an upper overlay that bypasses both ImageFS and EROFS.

The takeaway

The biggest improvement did not come from making individual host calls slightly faster. It came from removing those calls from the critical path entirely.

By giving the sentry direct access to filesystem metadata, EROFS turns many cross-boundary operations into ordinary memory lookups. That makes a substantial difference for modern development and agentic workloads, which frequently scan repositories, inspect dependencies, and operate across large numbers of small files.
