Making gVisor Filesystems Faster with EROFS

September 4, 2026

Development workloads spend a surprising amount of time asking the filesystem about files rather than reading them. Commands like find and ripgrep walk directory trees and inspect metadata for thousands of paths. Package managers and coding agents repeat those operations across entire repositories. Each lookup is small, but its fixed overhead adds up.

This summer at Modal, I worked on reducing that overhead for containers running inside gVisor. The existing filesystem required most file operations to cross into the host kernel. By switching container images to EROFS, gVisor could resolve metadata directly from memory and reserve host system calls for operations that actually need file contents.

The change made a representative agentic workload 3.7× faster and a directory-tree traversal 12.1× faster. Large reads remained at parity, while writes continued through the same upper overlay as before. The improvement was concentrated where we expected it: workloads dominated by path traversal and metadata access.

First, where does a container's filesystem come from?

A container is, roughly, a process with a root filesystem and a restricted view of the machine. Its image contains the operating-system files, libraries, packages, and application code assembled when the image was built. That image is mostly read-only; changes made while the container is running go into a separate writable overlay.

Downloading and unpacking an entire image before starting a container would be painfully slow. Modal instead uses a custom filesystem called ImageFS. ImageFS lazily serves container files from a multi-tier, content-addressed cache. Startup only needs a small metadata index; file contents can arrive later, when an application actually reads them. This is a great trade for cold-start latency because most files in a typical image are never touched.

Modal also runs untrusted workloads with gVisor. gVisor is an application kernel: from the sandboxed program's perspective it behaves like Linux, but its sentry implements the system-call interface in a userspace process. The host kernel sees the sentry, not the individual processes and kernel objects that the sentry is virtualizing.

That extra boundary is valuable for isolation, but boundaries are not free. If the sentry cannot answer a request itself, it has to make a real host system call. The way ImageFS exposed files made this especially noticeable for metadata-heavy workloads.

ImageFS made every file operation visit the host

ImageFS exposed a normal file tree owned by the host. An application call such as open, stat, readdir, or read first trapped into the gVisor sentry. To service it, the sentry issued a host system call into the host VFS.

If the requested data was already in the Linux page cache, the path could stop there. On a miss, the VFS forwarded the request through a FUSE mount to the ImageFS server, which resolved the file and fetched its contents from Modal's Blobnet storage layer when necessary.

This architecture is well suited to large reads. Once you ask for megabytes of file contents, the fixed cost of a system call and a few context switches is small relative to the data transfer. Metadata operations are the opposite: they do almost no useful work per call. Asking for a handful of inode fields can cost more in transitions than in data movement.

Tools that explore a filesystem amplify that fixed cost. find reads every directory entry and stats many of the paths it discovers. Package managers inspect thousands of files. Coding agents repeatedly search, inspect, edit, and re-scan repositories. With ImageFS, each small operation paid at least one trip into the host kernel, whether or not FUSE or Blobnet had any work to do.

EROFS lets the sentry answer for itself

EROFS, or Enhanced Read-Only File System, stores a filesystem as a block-structured image. Read-only container layers are a natural fit: their directory structure and metadata do not change after the image is built.

Instead of mounting a host-owned tree, we give the sentry a sparse EROFS image and memory-map it into the sentry's address space. gVisor's EROFS driver parses the superblock, inodes, directory entries, and file extents directly. Once that metadata is resident, a pathname lookup or stat is just gVisor reading memory it already owns. No host syscall is necessary.

A read still needs bytes. If they are not already available to the sentry, it issues a host call that travels through the VFS and FUSE mount. But the FUSE server now exposes one sparse image file instead of implementing the semantics of an entire directory tree. Blobnet and its caches remain responsible for supplying missing image data.

This distinction is the whole optimization: EROFS does not make crossing the boundary magically free. It gives the sentry enough structure to avoid crossing it unless the application actually needs file contents.

The distributions tell the story

The charts below are empirical cumulative distribution functions, or eCDFs. For any time on the horizontal axis, the curve's height is the fraction of benchmark runs that finished by then. A curve farther to the left is faster; a steep curve means the results are tightly clustered. EROFS is orange and ImageFS is blue.

Metadata-heavy workloads move decisively left

The broadest benchmark was agentic, a representative agent workflow that exercises the filesystem as part of a larger task. Its median runtime fell from 168.98 seconds to 45.33 seconds, a 3.7× speedup. The shape of the curve matters too: EROFS completes nearly every run before the ImageFS distribution reaches its slow cluster.

A focused tree walk makes the mechanism even clearer. find-all mostly asks the filesystem to enumerate directories and inspect entries. Those are precisely the operations that now stay inside the sentry, so its median falls from 2.78 seconds to 0.23 seconds.

The rest of the metadata-heavy benchmarks follow the same pattern:

Large reads stay where they were

A large read is dominated by moving data, not looking up metadata. Reads that miss the page cache still travel through the FUSE mount in both designs, so EROFS does not materially change their performance. The new representation removes metadata overhead without trading away the throughput behavior that ImageFS was designed for.

Writes bypass both lower filesystems

EROFS is read-only, but the container is not. gVisor sends writes to the writable upper layer of an overlay, which bypasses both ImageFS and EROFS. Write-heavy workloads therefore behave much as they did before; they do not exercise the read-only layer that this change is meant to accelerate.

A narrower interface to the host

EROFS does not replace the lazy loading or shared caching that made ImageFS useful. It changes the interface between gVisor and the container image. ImageFS asked the host to expose a file tree; with EROFS, the sentry understands the filesystem layout itself.

As a result, the host boundary is used mainly to retrieve file data, not to answer routine questions about paths and metadata. That is a smaller architectural change than replacing the storage system, but it removes repeated fixed costs from some of the most common filesystem operations.

The benchmark profile follows directly from that design. Metadata-heavy tools improve substantially, large reads remain unchanged, and writes continue to bypass the read-only image. For repository scans, package installation, and agentic workloads, eliminating the host round trip from each lookup compounds into a much larger end-to-end improvement.
